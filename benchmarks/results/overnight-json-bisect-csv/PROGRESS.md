## Generator design worth trying
A generator-expression object can own a stable environment containing its target bindings plus a stack of iterators. Compile body/filter/nested-iterable expressions into zero-argument HIR functions and execute those directly with execute_frame using that SAME generator environment, rather than creating a fresh closure environment per yield. This preserves lazy evaluation, late binding of yielded lambdas, stable name caches and outer captures without introducing general yield statements or a suspended bytecode frame. Evaluate/acquire the outermost iterator immediately in the enclosing scope, as Python does; evaluate inner iterable/filter/body callbacks lazily while next() advances nested iterator layers. Store config functions as Rc<HIR> and trace environment+iterators from the generator object. Move state out with a Running sentinel during execution, publish transient roots while callbacks/GC run, reject reentry, and close on errors. Reuse existing comprehension/lambda builder capture analysis. Explicitly unsupported syntax is better than incorrect eager semantics.
